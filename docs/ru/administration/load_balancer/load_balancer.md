## {heading(Управление метаданными агрегата)[id=load_balance_host_aggregate_metadata_edition]}

Автоматическая балансировка выполняется на основе настроек агрегатов: эти настройки заключаются в указании метаданных для каждого агрегата. В качестве примера балансировки можно привести закрепление вычислительного узла за проектом (подробнее — в разделе {linkto(../../administration/infrastructure_management_main/infrastructure_management_hypervisor#dedicated_compute_node)[text=%text]}), когда необходимо, чтобы ресурсы данного узла были доступны только в рамках этого проекта.

<info>

Управление метаданными выполняется с помощью Портала администратора.

</info>

Чтобы просмотреть список метаданных агрегата:

1. Перейдите в раздел **Администрирование** → **Агрегаты узлов**.
1. Нажмите на значок слева от поля поиска и выберите вариант **Реальные данные** (по умолчанию показаны **Кешированные данные**).
1. Нажмите на значок **•••** справа от названия агрегата и выберите пункт **Обновление метаданных**.

<info>

Для добавления доступны следующие группы метаданных (допускается указание только одного свойства из группы):

* Типы агрегатов:

   * `agg_common=true` — стандартные публичные гипервизоры.
   * `agg_freq=true` — высокочастотные процессоры.
   * `agg_heavy=true` — указывается при ОЗУ больше 64 ГБ.
   * `agg_nested=true` — поддержка вложенной виртуализации.
    <!--- //** `agg_nexus=true` — #todo уточнить описание метаданных -->
   * `agg_gpu=true` — гипервизоры с видеокартами.

* Типы процессоров:

   * `mcs:cpu_type=standart` — стандартные процессоры.
   * `mcs:cpu_type=hpc` — высокочастотные процессоры.
   * `hw:cpu_sockets='1'` — указывается при CPU меньше 12.
   * `hw:cpu_sockets='2'` — указывается при CPU большем, либо равным 12.

* Типы зон:

   * `availability_zone='AZ1'`
   {ifndef(cer)}
   * `agg_octavia=true` — установить агрегат доступным для разворачивания Octavia.
   {/ifndef}

</info>

Чтобы добавить новые или редактировать существующие метаданные агрегата:

1. Откройте список метаданных агрегата (описание процесса приведено в предыдущей инструкции).
1. Нажмите кнопку **Редактировать**.
1. Добавьте метаданные из области слева или укажите пользовательские метаданные в формате **Имя-Значение** в одноимённых полях.
1. Нажмите кнопку **Сохранить изменения**.

Дальнейшая балансировка будет выполняться в соответствии с указанными метаданными для агрегата.

## {heading(Миграция ресурсов гипервизоров)[id=load_balance_hypervisors_migration]}

Миграция ресурсов гипервизоров позволяет оперативно разгрузить перегруженный вычислительный узел. При миграции определяются ВМ-кандидаты на миграцию, после чего их можно переместить на наименее загруженные вычислительные узлы.

<err>

Для корректного выполнения миграции ресурсов гипервизоров должны быть соблюдены следующие условия:

{ifndef(cer)}
* ВМ созданы на основе Типа инстанса (flavor), у которых установлены метаданные `agg_common=true`; шаги по добавлению метаданных в шаблон приведены в разделе {linkto(../../usage/iaas_main/iaas_vm_templates#v_infra_flavor_set)[text=%text]}. После данного действия других манипуляций с ВМ не требуется.
{/ifndef}

* Агрегат, принимающий участие в миграции, должен иметь метаданные `agg_common=true`. Шаги по добавлению метаданных для агрегата приведены в разделе {linkto(#load_balance_host_aggregate_metadata_edition)[text=%text]}.

</err>

Чтобы выполнить миграцию ресурсов гипервизоров, используйте один из интерфейсов:

* Портал администратора.
* OpenStack CLI.

### {heading(Портал администратора)[id=load_balance_hypervisors_migration_sa]}

Чтобы выполнить миграцию ресурсов гипервизоров в Портале администратора:

1. Перейдите в раздел **Администрирование** → **Вычислительные узлы**.
1. Выберите один или несколько гипервизоров, которые будут участвовать в миграции, отметив флажок в списке. Степень их загруженности отображается в столбцах `cpu_idle` (остаток свободного CPU в процентах к сумме ядер) и `free_mem` (остаток свободного ОЗУ в МБ).
1. Нажмите кнопку **Мигрировать** над таблицей. Задайте параметры:

   * **Использование процессора** — целевая процентная нагрузка по CPU после выполнения миграции. Например, значение `0.5` означает загрузку на 50% по CPU (пояснения приведены ниже).

      <warn>

      При расчёте использования процессора гипервизоров учитывается только реальное потребление CPU со стороны ВМ, не максимум, установленный для шаблона ВМ.

      </warn>
   * **Использование памяти** — целевой объём ОЗУ в МБ после выполнения миграции. Учитывается максимальный объём, указанный в шаблоне ВМ.

      <info>

      Значения параметров CPU и ОЗУ позволят найти ВМ-кандидатов для освобождения ресурсов гипервизора/гипервизоров до выбранных значений. Например, гипервизор загружен на 100% по CPU и на 128ГБ по ОЗУ, и выбраны значения `0.5` и `65536` соответственно. Для миграции будут доступны ВМ, значения параметров которых превышают эти значения. После миграции выбранных ВМ нагрузка на целевом гипервизоре/гипервизорах изменится до заданных значений.

      Требования к выбору ВМ-кандидатов:

      1. Ни одно из заданных значений параметров CPU и ОЗУ не достигнуто.
      1. Актуальные значения параметров максимально приближены к заданным значениям. На ВМ нагрузка по CPU непостоянна, поэтому при анализе значений может наблюдаться небольшая погрешность.

      </info>
     
   * **Ограничение количества ВМ для миграции** — максимальное количество ВМ для миграции.
   * **Название зоны для живой миграции** — название зоны доступности (AZ), в рамках которой выполняется миграция. Используется в случае наличия на нескольких гипервизорах нескольких AZ.
   * **Название агрегата для живой миграции** — название агрегата узлов, в рамках которого будет выполняться миграция. Это позволит ограничить список миграций только ВМ определённых агрегатов и не затронуть остальные.
   * **Включить VIP-проекты** — опция включения VIP-проектов. ВМ, помеченные как VIP, не будут участвовать в расчётах и останутся на текущем вычислительном узле. Включение опции вызовет большее количество миграций обычных (не VIP) ВМ. VIP ВМ будут рассчитываться в качестве кандидатов наравне с другими ВМ.
   * **Игнорировать отключенные гипервизоры** — позволять использовать отключенные вычислительные узлы в качестве кандидатов для миграции. Отключенные вычислительные узлы будут рассматриваться как потенциальные кандидаты для миграции наравне с включёнными.

      <info>

      Опция **Игнорировать отключенные гипервизоры** может быть полезна в следующих случаях:

      * ВМ, которые планируется добавлять в этот агрегат, уже существуют, но сам агрегат нельзя включать, чтобы не допустить размещения на нём нежелательных ВМ.
      * Некоторые ВМ требуется временно переместить на отключенные вычислительные узлы, находящиеся в резерве.

      </info>

1. Нажмите кнопку **Следующий шаг**.
1. Выберите ВМ, подходящие для выполнения миграции. Если найденные ВМ не подходят для миграции, нажмите кнопку **Предыдущий шаг** и измените параметры поиска.
1. При необходимости укажите хост назначения:

   <err>

   При выборе хоста назначения выполняется принудительная миграция. Это может привести к перезагрузке целевого вычислительного узла. Если хост назначения не указан, вычислительные узлы для миграции определяются автоматически.

   </err>

   1. Нажмите кнопку **Хост назначения: отключено**.
   1. Включите переключатель **Включен**.
   1. В поле **Хост назначения** укажите целевой хост, куда будет выполнена миграция.
   1. Нажмите кнопку **Применить**.

1. Выберите одну или несколько ВМ, которые будут отправлены на миграцию.

   <warn>

   Если ВМ отображается серым цветом и не позволяет отметить её в списке — это значит, что данная ВМ выбрана как кандидат на миграцию, но для неё нет свободных ресурсов для миграции. В этом случае рекомендуется либо увеличить значения CPU/RAM для миграции, либо подключить новые вычислительные узлы.

   </warn>
   
1. Нажмите кнопку **Завершить**.

<info>

Если в списке ВМ на шаге **Доступные миграции** не найдено ни одной ВМ:

* Убедитесь, что указана опция `agg_common=true` для типа инстанса и агрегата. Такие ВМ и гипервизоры не будут участвовать в работе данного инструмента.
* Выполните поиск с другими параметрами на шаге **Настройки**: в {var(sys3)} не было найдено ВМ-кандидатов, подходящей под установленные критерии.

</info>

После запуска процесса миграции отследить его ход можно в разделе **Облачные вычисления** → **Экземпляры ВМ** при выборе типа данных **Реальные данные**. История миграции ВМ доступна в разделе **Администрирование** → **Миграции**.

### {heading(OpenStack CLI)[id=load_balance_hypervisors_migration_cli]}

В отличие от миграции с помощью Портала администратора, миграция с использованием OpenStack CLI не имеет количественных параметров и предназначена для миграции всех инстансов с целевого гипервизора.

Миграция ресурсов гипервизоров в OpenStack CLI выполняется следующей командой:

```console
$ nova host-servers-migrate <HOST>
```

Здесь `<HOST>` — название целевого гипервизора, откуда будет осуществлена полная миграции.

## {heading(Управление нагрузкой с помощью правил планировщика (sheduler))[id=load_balance_sheduler_setting]}

Настройки правил планировщика находятся на управляющем узле в конфигурационном файле Nova (`nova.conf`). Чтобы изменить правила размещения ВМ на агрегатах:

1. Выполните подготовительные операции (подробнее — в разделе {linkto(../../usage/interfaces_access#use_openstackcli_admin)[text=%text]}).
1. Найдите параметр `scheduler_available_filters` в конфигурационном файле `nova.conf`.
1. Добавьте/удалите фильтры (полный список фильтров приведён в документации [**Compute schedulers**](https://docs.openstack.org/ocata/config-reference/compute/schedulers.html) OpenStack).
1. Сохраните файл и перезагрузите сервис `openstack-nova-scheduler` на всех управляющих узлах:

   ```console
   # systemctl restart openstack-nova-scheduler
   ```

<err>

В инструкции выше показан функциональный пример управления нагрузкой с помощью правил планировщика. В стандартном случае выполняйте настройку через Ansible.

</err>

## {heading(Политики affinity и anti-affinity для размещения ВМ)[id=load_balance_affinity_policy]}

Правила размещения ВМ на узлах кластера может настраиваться политиками, в частности, с политикой `affinity` ВМ будут создаваться только на одном узле, а с `anti-affinity` — только на разных (или с максимальным распределением по узлам, если создаваемых ВМ больше, чем узлов). Далее приведён пример добавления политик `affinity` и `anti-affinity`.

<err>

Для корректной работы политик `affinity` и `anti-affinity` необходимо наличие в кластере не менее двух активных вычислительных узлов.

</err>

Чтобы добавить политики `affinity` и `anti-affinity`:

1. Выполните подготовительные операции (подробнее — в разделе {linkto(../../usage/interfaces_access#use_openstackcli_admin)[text=%text]}).
1. Создайте группы серверов с политиками `affinity` и `anti-affinity`, выполнив команды:

   ```console
   # openstack --insecure server group create --policy anti-affinity anti-affinity-group
   # openstack --insecure server group create --policy affinity affinity-group
   ```

1. Отобразите список созданных групп:

   ```console
   # openstack --insecure server group list
   ```

   {caption(Пример отображения информации о группах серверов)[align=left;position=above]}
   ```console
   +--------------------------------------+---------------------+---------------+
   | ID                                   | Name                | Policies      |
   +--------------------------------------+---------------------+---------------+
   | ae7a655b-4b18-425b-82cb-415930669d7b | anti-affinity-group | anti-affinity |
   | bd5a029e-1fb2-4133-b019-a52eed372fcb | affinity-group      | affinity      |
   +--------------------------------------+---------------------+---------------+
   ```
   {/caption}

Чтобы убедиться в корректности работы политик, одновременно создайте несколько ВМ, указав для них политики `affinity` и `anti-affinity`:

```console
# for i in 1 2 3;do openstack --insecure server create --image <НАЗВАНИЕ_ОБРАЗА> --flavor Basic-1-1 --hint group=<ID_ГРУППЫ_СО_СВОЙСТВОМ_AFFINITY> --nic net-id=<ID_СЕТИ> vm-affinity-$i;done

# for i in 1 2;do openstack --insecure server create --image <НАЗВАНИЕ_ОБРАЗА> --flavor Basic-1-1 --hint group=<ID_ГРУППЫ_СО_СВОЙСТВОМ_ANTI-AFFINITY> --nic net-id=<ID_СЕТИ> vm-anti-affinity-$i;done
```

ВМ будут размещены в соответствии с применённой политикой.
