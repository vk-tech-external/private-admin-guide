# {heading(Миграция ВМ между гипервизорами)[id=migration_vm]}

## {heading(Живая миграция ВМ между гипервизорами)[id=live_migration_vm]}

Процесс живой миграции в реальном времени переносит работающую ВМ с одного узла на другой. Все свойства ВМ, в том числе IP-адреса, метаданные, память, состояние сетей, операционных систем и приложений, остаются неизменными. Выбираемый для миграции узел должен быть включен.

ВМ могут мигрировать только между гипервизорами с процессорами одинаковой архитектуры. Примеры: с Intel на Intel, с AMD на AMD.

Если у ВМ есть снимки (снэпшоты) диска внешней СХД, живая миграция недоступна. Снимки создают зависимость от исходного состояния диска, что делает процесс переноса данных в реальном времени невозможным. Чтобы запустить процесс живой миграции, используйте один из способов:  

* Удалите снимок диска ВМ (подробнее — в документе **Руководство пользователя {var(system)}** в разделе **Облачные вычисления** → **Диски** → **Управление снимками диска** → **Портал самообслуживания** → **Удаление снимка диска**). 
* Создайте резервную копию из снимка (подробнее — в документе **Руководство пользователя {var(system)}** в разделе **Облачные вычисления** → **Диски** → **Создание диска**).
* Запустите процесс холодной миграции (подробнее — в разделе {linkto(#hold_migration_vm)[text=%text]}).

Чтобы выполнить живую миграцию ВМ, используйте один из интерфейсов:

* Портал администратора.
* OpenStack CLI.

### {heading(Живая миграция с кешированными данными ВМ)[id=live_migration_vm_cached]}

Чтобы запустить процесс живой миграции с кешированными данными ВМ через Портал администратора:

1. Перейдите в раздел **Облачные вычисления** → **Экземпляры ВМ**.

1. Нажмите на значок **с** и выберите **Кешированные данные**.

1. Выберите ВМ и нажмите кнопку **Мигрировать**.

1. Выберите тип миграции: **Базовая миграция** или **Продвинутая миграция**. 

   <info>

   Если необходимо установить зону доступности для миграции, выберите продвинутый тип.

   </info>

1. Настройте параметры, по которым будут найдены варианты миграции:

   * **Использование процессора** — допустимое количество мощности процессора, которое может использоваться для миграции. 
   * **Использование памяти** — допустимый объем памяти, который может использоваться в процессе миграции. 
   * **Ограничение количества ВМ для миграции** — допустимое количество ВМ в рамках миграции.
   * **Игнорировать отключенные гипервизоры** — при выборе узла для миграции будут исключены отключенные узлы.

1. Нажмите кнопку **Подобрать варианты миграции**.

1. Выберите один из вариантов миграции со статусом **Готово**.

1. При необходимости установите переключатель **Указать Hypervisor назначения вручную** и укажите узел, на который будет перенесена ВМ.

1. Нажмите кнопку **Мигрировать**.

### {heading(Живая миграция с реальными данными ВМ)[id=live_migration_vm_data]}

Чтобы запустить процесс миграции с реальными данными ВМ без ее отключения через Портал администратора:

1. Перейдите в раздел **Облачные вычисления** → **Экземпляры ВМ**.

1. Нажмите на значок **с** и выберите **Реальные данные**. 

1. Нажмите на значок **•••** в строке ВМ и выберите **Живая миграция инстанса**.

1. На странице **Живая миграция** укажите текущий и новый узел для переноса ВМ и нажмите кнопку **Начать живую миграцию**.

## {heading(Холодная миграция ВМ между гипервизорами)[id=hold_migration_vm]}

Холодная миграция — процесс переноса отключенной ВМ между гипервизорами.

Для холодной миграции ВМ между инсталляциями {var(sys2)} с сохранением IPv4-адреса ВМ используется автоматический анонс сетевых маршрутов (/32) до ВМ. Пример: ВМ, являющаяся инстансом БД или бэкендом сервиса, может быть перенесена из одной инсталляции {var(sys2)} в другую.

<warn>

В текущей реализации отсутствует возможность использования общей внешней сети на инсталляцию. Необходимое количество провайдерских сетей должно быть добавлено в проекты.

</warn>

Для отправки /32 анонсов используется BGP Dynamic Routing. На сетевых узлах утилита `nbgp` формирует необходимые маршруты до ВМ через IP-адрес гипервизора, основываясь на записях в БД Neutron, и анонсирует эти маршруты с помощью `gobgp`. Изоляция маршрутизации внешних сетей по BGP осуществляется на вычислительных узлах с помощью сетевых пространств имен Linux.

Перед началом миграции:

1. Перейдите в раздел **Администрирование** → **Вычислительные узлы** и убедитесь, что существует не менее двух активных вычислительных узлов.

1. Убедитесь, что создана ВМ с:

   * Новой сетью с доступом к внешней сети.
   * Группой безопасности `all`.
   * Внешним IP. 
   
1. Сохраните файл ключевой пары ВМ.

1. Скопируйте идентификатор ВМ (ВМ_ID).

Запустить холодную миграцию ВМ между гипервизорами можно с помощью команд OpenStack CLI:

1. Выполните вход на деплой-ноду по SSH (подробнее — в разделе {linkto(../../../../interfaces_access#deploy_host_auth)[text=%text]}).

1. Выполните Bash-скрипт из файла `~root/openrc.sh`:

   ```console
   # source ~root/openrc.sh
   ```
1. Выполните команду:

   ```console
   # openstack server show <ВМ_ID>
   ```
   Ответ команды будет содержать данные ВМ. Значение строки `OS-EXT-SRV-ATTR:host` — `kcn00x`.

1. Добавьте в файл содержимое ключевой пары ВМ, выполнив команду редактора nano:
   
   ```console
   # nano test.pem
   ```
1. Подключитесь к ВМ, выполнив команду
   
   ```console
   # ssh -i test.pem <ИМЯ_ПОЛЬЗОВАТЕЛЯ>@<ВНЕШНИЙ_IP>
   ```
1. Проверьте адрес ВМ, выполнив команду:

   ```console
   # ip route
   ```
1. Отключитесь от ВМ.
   
1. Выполните команду:
   
   ```console
   # neutron-bgp-manage-adv-ip list
   ```
   {caption(Пример ожидаемого результата)[align=left;position=above]}
   
   ```console
   [{'bgp_speaker_id': '77abecc2-2379-4857-bc95-a28294b33d2c',
   'host': 'kcn001',
   'id': '98f19780-dfec-4c2a-982a-22409d089730',
   'ip': '10.30.50.10'}]
   ```
   {/caption}

   Скопируйте в разделе `host` значение параметра `ip`.

1. Откройте второе окно терминала и выполните вход на деплой-ноду по SSH.

1. Перейдите на узел физической сети, выполнив команды:

   ```console
   # ssh router
   # sudo bash
   ```
1. Проверьте, что ВМ доступна, выполнив команду:

   ```console
   # ping <ВНЕШНИЙ_IP>
   ```
1. Выполните команду:

   ```console
   # vtysh -c "show ip route <ВНЕШНИЙ_IP>/32"
   ```
   {caption(Пример ожидаемого результата)[align=left;position=above]}

   ```console
   [root@router centos]# vtysh -c "show ip route 100.60.0.31/32"
   Routing entry for 100.60.0.31/32
   Known via "bgp", distance 20, metric 0, best
   Last update 00:25:58 ago
   100.60.0.1 (recursive), weight 1
   10.30.50.10, via eth4, weight 1
   ```
   {/caption}

   Здесь IP-адрес `10.30.50.10` должен быть идентичным скопированному на шаге 8.

1. В первом окне терминала остановите ВМ:

   ```console
   # openstack server stop <ВМ_ID>
   ```
1. Запустите холодную миграцию ВМ:

   ```console
   # openstack server migrate <ВМ_ID>
   ```
1. Запустите ВМ:

   ```console
   # openstack server start <ВМ_ID>
   ```
1. Убедитесь, что ВМ запущена на необходимом узле:

   ```console
   openstack server show <ВМ_ID>
   ```
1. Подключитесь к ВМ:

   ```console
   # ssh -i test.pem <ИМЯ_ПОЛЬЗОВАТЕЛЯ>@<ВНЕШНИЙ_IP>
   ```
1. Проверьте адрес ВМ, выполнив команду:

   ```console
   # ip route
   ```
