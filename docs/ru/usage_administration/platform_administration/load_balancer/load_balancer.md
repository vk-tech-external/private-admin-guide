# {heading(Балансировка нагрузки)[id=load_balancer]}

В {var(sys3)} предусмотрены следующие виды балансировки:

1. Балансировка на уровне администраторов {var(sys2)}:

   * Автоматическая балансировка, регулируемая метаданными агрегата (см. раздел {linkto(#load_balance_host_aggregate_metadata_edition)[text=%text]}).
   * Ручная балансировка с помощью миграции ресурсов гипервизоров (см. раздел {linkto(#load_balance_hypervisors_migration)[text=%text]}).
   * Распределение нагрузки на агрегатах с помощью правил планировщика (sheduler); см. раздел {linkto(#load_balance_sheduler_setting)[text=%text]}.
   * Настройка правил размещения ВМ на вычислительных узлах (affinity, anti-affinity), см. раздел {linkto(#load_balance_affinity_policy)[text=%text]}.

1. Балансировка на уровне администраторов проектов:

   * Octavia balancer — распределяет задания/трафик между несколькими сетевыми устройствами (например, серверами) с целью оптимизации использования ресурсов, сокращения времени обслуживания запросов, горизонтального масштабирования кластера (динамическое добавление/удаление устройств), а также обеспечения отказоустойчивости (см. раздел {linkto(../../../usage_administration/v_infrastructure_management#load_balancer_manage)[text=%text]}).

## {heading(Управление метаданными агрегата)[id=load_balance_host_aggregate_metadata_edition]}

Автоматическая балансировка выполняется на основе настроек агрегатов: эти настройки заключаются в указании метаданных для каждого агрегата. В качестве примера балансировки можно привести закрепление вычислительного узла за проектом (см. раздел {linkto(../../../usage_administration/platform_administration/infrastructure_management#dedicated_compute_node)[text=%text]}), когда необходимо, чтобы ресурсы данного узла были доступны только в рамках этого проекта.

<info>

Управление метаданными выполняется с помощью Портала администратора.

</info>

Чтобы посмотреть список метаданных агрегата:

1. В меню слева перейдите в раздел «Облачные вычисления» → «Агрегаторы узлов».
1. Нажмите на иконку справа от поля поиска и выберите вариант «Реальные данные» (по умолчанию показаны «Кешированные данные»).
1. Нажмите на кнопку «•••» справа от названия агрегата и выберите пункт «Обновление метаданных».

Чтобы добавить новые / редактировать существующие метаданные агрегата:

<info>

Для добавления доступны следующие группы метаданных (допускается указание только одного свойства из группы):

* Типы агрегатов:

   * `agg_common=true` — стандартные публичные гипервизоры.
   * `agg_freq=true` — высокочастотные процессоры.
   * `agg_heavy=true` — указывается при ОЗУ больше 64 ГБ.
   * `agg_nested=true` — поддержка вложенной виртуализации.
   * `agg_gpu=true` — гипервизоры с видеокартами.

* Типы процессоров:

   * `mcs:cpu_type=standart` — стандартные процессоры.
   * `mcs:cpu_type=hpc` — высокочастотные процессоры.
   * `hw:cpu_sockets='1'` — указывается при CPU меньше 12.
   * `hw:cpu_sockets='2'` — указывается при CPU большем, либо равным 12.

* Типы зон:

   * `availability_zone='AZ1'`

* `agg_octavia=true` — установить агрегат доступным для разворачивания Octavia.

</info>

1. Откройте список метаданных агрегата (см. шаги предыдущей инструкции).
1. Нажмите на кнопку «Редактировать».
1. Добавьте метаданные из области слева (если таковые имеются) или укажите пользовательские метаданные в формате «Имя-Значение» в одноимённых полях.
1. Нажмите на кнопку «Сохранить изменения».

Дальнейшая балансировка будет выполняться в соответствии с указанными метаданными для агрегата.

## {heading(Миграция ресурсов гипервизоров)[id=load_balance_hypervisors_migration]}

Миграция ресурсов гипервизоров позволяет оперативно разгрузить перегруженный вычислительный узел. При миграции определяются ВМ-кандидаты на миграцию, после чего их можно переместить на наименее загруженные вычислительные узлы.

<err>

Для корректного выполнения миграции ресурсов гипервизоров должны быть соблюдены следующие условия:

* ВМ созданы на основе Типа инстанса (flavor), у которых установлены метаданные `agg_common=true`; шаги по добавлению метаданных в шаблон см. в разделе {linkto(#v_infra_flavor_set)[text=%text]}. После данного действия других манипуляций с ВМ не требуется.
* Агрегат, принимающий участие в миграции, должен иметь метаданные `agg_common=true`; шаги по добавлению метаданных для агрегатора см. в разделе {linkto(#load_balance_host_aggregate_metadata_edition)[text=%text]}.

</err>

Миграция ресурсов гипервизоров осуществляется при помощи:

* Портала администратора.
* OpenStack CLI.

### {heading(Портал администратора)[id=hypervisor_resources_migration_SA]}

Чтобы выполнить миграцию ресурсов гипервизоров в Портале администратора:

1. В меню слева перейдите в раздел «Облачные вычисления» на страницу «Гипервизоры».
2. Выберите один или несколько гипервизоров, которые будут участвовать в миграции, отметив флажок в списке. Степень их загруженности отображается в столбцах `cpu_idle` (остаток свободного CPU в процентах к сумме ядер) и `free_mem` (остаток свободного ОЗУ в МБ).
3. Нажмите на кнопку «Мигрировать» над таблицей. В открывшейся форме имеются поля:
   
   * Использование процессора гипервизоров — целевая процентная нагрузка по CPU после выполнения миграции. Например, значение `0.5` означает загрузку на 50% по CPU (см. пояснения ниже).

      <warn>

      При расчёте использования процессора гипервизоров учитывается только реальное потребление CPU со стороны ВМ, не максимум, установленный для шаблона ВМ.

      </warn>

   * Использование физической памяти гипервизоров — целевой объём ОЗУ в МБ после выполнения миграции. Учитывается именно максимальный объём, указанный в шаблоне ВМ (см. пояснения ниже).
   
      <info>
         
      Указанные выше параметры по CPU и ОЗУ позволят найти ВМ-кандидатов для освобождения ресурсов указанного гипервизора или гипервизоров до выбранных параметров. Например, если существовал загруженный на 100% по CPU и на 128ГБ по ОЗУ гипервизор, и были выбраны значения `0.5` и `65536` соответственно, то будет доступным некоторое количество ВМ для миграции. После миграции найденных ВМ-кандидатов нагрузка на целевом гипервизоре или гипервизорах изменится до указанных значений.
         
      Учтите, что выбор ВМ-кандидатов происходит по логике «И»: с одной стороны, ВМ-кандидаты больше не будут искаться, если гипервизор стал удовлетворять хотя бы по одному из двух вышеуказанных параметров; с другой — в ВМ-кандидаты будут выбираться такие ВМ, которые позволят максимально приблизиться к заданным параметрам. Если учесть, что на ВМ может быть не постоянная нагрузка по CPU, то в данном инструменте может наблюдаться небольшая погрешность.

      </info>

   * Включить VIP-проекты — опция включения VIP-проектов. ВМ, помеченные как VIP, не будут участвовать в расчётах и останутся на текущем вычислительном узле в любом случае, но это вызовет большее количество миграций обычных (не VIP) ВМ. При включении этой опции VIP ВМ будут рассчитываться в качестве кандидатов наравне с другими ВМ.
   * Название зоны — наименование зоны доступности (AZ), в рамках которой выполняется миграция. Используется в случае наличия на нескольких гипервизорах нескольких AZ.
   * Название агрегатора — наименование агрегата узлов, в рамках которого будет выполняться миграция. Это позволит вам ограничить список миграций только ВМ определённых агрегатов и не трогать остальные.
   * Игнорировать выключенные гипервизоры — позволять использовать выключенные вычислительные узлы в качестве кандидатов для миграции. Выключенные вычислительные узлы будут рассматриваться как потенциальные кандидаты для миграции наравне с включёнными.

      <info>
         
      Опция «Игнорировать выключенные гипервизоры» может быть полезна в следующих случаях:
         
      * ВМ, которые планируется добавлять в этот агрегат, уже существуют, но сам агрегат нельзя включать, чтобы не допустить размещения на нём нежелательных ВМ.
      * Некоторые ВМ требуется временно переместить на выключенные вычислительные узлы, находящиеся в резерве.
      
      </info>

4. Заполните поля формы и нажмите на кнопку «Следующий шаг».
5. В открывшейся таблице из найденных ВМ выберите подходящие для выполнения миграции. Если найденные ВМ по каким-то причинам не подходят для миграции, нажмите на кнопку «Предыдущий шаг» и измените параметры поиска.
6. При необходимости укажите хост назначения:

   <warn>

   Выбор хоста назначения подразумевает выполнение принудительной миграции, что может привести к перезагрузке целевого вычислительного узла. Если не указывать хост назначения, то вычислительные узлы для миграции будут определены автоматически.

   </warn>
   
   1. Нажмите на кнопку «Хост назначения: отключено».
   1. В открывшейся форме включите переключатель «Включен».
   1. В поле «Хост назначения» укажите целевой хост, куда будет выполнена миграция.
   1. Нажмите на кнопку «Применить».
7. Выберите одну или несколько ВМ, которые будут отправлены на миграцию.

   <warn>

   Если ВМ отображается серым цветом и не позволяет отметить её в списке — это значит, что данная ВМ выбрана как кандидат на миграцию, но для неё нет свободных ресурсов для миграции. В этом случае рекомендуется либо увеличить значения CPU/RAM для миграции, либо подключить новые вычислительные узлы.

   </warn>

8. Нажмите на кнопку «Завершить».

<info>

Если в списке ВМ на шаге «Доступные миграции» не найдено ни одной ВМ:

* Убедитесь, что указана опция `agg_common=true` для типа инстанса и агрегатора. В итоге такие ВМ и гипервизоры не будут участвовать в работе данного инструмента.
* Выполните поиск с другими параметрами на шаге «Настройки»: в {var(sys3)} не было найдено ВМ-кандидатов, подходящей под установленные критерии.

</info>

После запуска процесса миграции отследить его ход можно в разделе «Облачные вычисления» → «Инстансы» при выборе типа данных «Реальные данные». История миграции ВМ доступна в разделе «Облачные вычисления» → «Миграции».

### {heading(OpenStack CLI)[id=hypervisor_resources_migration_CLI]}

В отличие от миграции с помощью Портала администратора, миграция с использованием OpenStack CLI не имеет количественных параметров и предназначена для миграции всех инстансов с целевого гипервизора.

Миграция ресурсов гипервизоров в OpenStack CLI выполняется следующей командой:

```bash
nova host-servers-migrate <HOST>
```

, где `<HOST>` — наименование целевого гипервизора, откуда будет осуществлена полная миграции.

## {heading(Управление нагрузкой с помощью правил планировщика (sheduler))[id=load_balance_sheduler_setting]}

Настройки правил планировщика находятся на управляющем узле в конфигурационном файле Nova (`nova.conf`). Чтобы изменить правила размещения ВМ на агрегатах:

1. Выполните подготовительные операции (см. раздел {linkto(../../../usage_administration/interfaces_access#use_openstackcli_admin)[text=%text]}).
1. Найдите параметр `scheduler_available_filters` в конфигурационном файле `nova.conf`.
1. Добавьте / удалите фильтры (полный список фильтров см. в документации [«Compute schedulers»](https://docs.openstack.org/ocata/config-reference/compute/schedulers.html) Openstack).
1. Сохраните файл и перезагрузите сервис `openstack-nova-scheduler` на всех управляющих узлах:
   
   ```bash
   systemctl restart openstack-nova-scheduler
   ```

<err>

В инструкции выше показан функциональный пример управления нагрузкой с помощью правил планировщика. В стандартном случае выполняйте настройку через Ansible.

</err>

## {heading(Политики affinity и anti-affinity для размещения ВМ)[id=load_balance_affinity_policy]}

Правила размещения ВМ на узлах кластера также может настраиваться политиками, в частности, с политикой `affinity` ВМ будут создаваться только на одном узле, а с `anti-affinity` — только на разных (или с максимальным распределением по узлам, если создаваемых ВМ больше, чем узлов). Далее приведён пример добавления политик `affinity` и `anti-affinity`.

<err>

Для корректной работы политик `affinity` и `anti-affinity` необходимо наличие в кластере не менее двух активных вычислительных узлов.

</err>

Чтобы добавить политики `affinity` и `anti-affinity`:

1. Выполните подготовительные операции (см. раздел {linkto(../../../usage_administration/interfaces_access#use_openstackcli_admin)[text=%text]}).
1. Создайте группы серверов с политиками `affinity` и `anti-affinity`, выполнив команды:
   
   ```bash
   openstack --insecure server group create --policy anti-affinity anti-affinity-group
   openstack --insecure server group create --policy affinity affinity-group
   ```

1. Отобразите список созданных групп:
   
   ```bash
   openstack --insecure server group list
   ```

   {caption(Пример отображения информации о группах серверов)[align=left;position=above]}
   ```bash
   +--------------------------------------+---------------------+---------------+
   | ID                                   | Name                | Policies      |
   +--------------------------------------+---------------------+---------------+
   | ae7a655b-4b18-425b-82cb-415930669d7b | anti-affinity-group | anti-affinity |
   | bd5a029e-1fb2-4133-b019-a52eed372fcb | affinity-group      | affinity      |
   +--------------------------------------+---------------------+---------------+
   ```
   {/caption}

Чтобы убедиться в корректности работы политик, одновременно создайте несколько ВМ, указав для них политики `affinity` и `anti-affinity`:

```bash
for i in 1 2 3;do openstack --insecure server create --image <НАЗВАНИЕ_ОБРАЗА> --flavor Basic-1-1 --hint group=<ID_ГРУППЫ_СО_СВОЙСТВОМ_AFFINITY> --nic net-id=<ID_СЕТИ> vm-affinity-$i;done

for i in 1 2;do openstack --insecure server create --image <НАЗВАНИЕ_ОБРАЗА> --flavor Basic-1-1 --hint group=<ID_ГРУППЫ_СО_СВОЙСТВОМ_ANTI-AFFINITY> --nic net-id=<ID_СЕТИ> vm-anti-affinity-$i;done
```

ВМ будут размещены в соответствии с применённой политикой.
